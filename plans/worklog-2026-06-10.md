## Adversarial plan review

- Found: the original two-commit split put PrivacyInfo.xcprivacy (and the policy
  / data-safety docs claiming an opt-out) in commit 2, while commit 1 flipped
  collection on. Commit 1 would then ship code that collects with a manifest
  declaring it does not, which is individually incorrect on compliance. Fixed:
  collapse to a single commit; collection, its declaration, and the opt-out land
  together.
- Held: env-var opt-out still wins in resolve precedence (devs/CI unaffected);
  AppDefault is constructed immediately so no dead-variant warning; reading the
  disabled marker defaults to ON when the config dir is unreadable, matching the
  first_run safe-default pattern and the on-by-default intent.

## Decisions made

- Tri-state via two independent prefs (enabled marker + existing custom key)
  rather than a sentinel in api_secret.txt. Keeps api_secret.txt meaning intact
  and mirrors the first_run marker pattern already in the codebase.
- Replace `SavedOverride` with `AppDefault { disabled, custom }` rather than add
  a third variant, to avoid a dead-variant clippy warning and keep one app path.
- Follow the existing `tokio::sync::watch` telemetry channel rather than
  introducing n0_watcher for this change.

## Staff reviews

Round 1: four adversarial reviewers (Rust, docs/QA, concurrency, privacy) on the
committed diff.

Review-of-reviews, findings that survived the opposing stance and were fixed
(amended into the feature commit, now a668a3e):

- Critical (docs/QA): the privacy-policy summary bullet and the user-facing
  listing description still said "sends no data by default", contradicting the
  new on-by-default sections. Both flipped.
- Substantive (Rust + concurrency): the toggle handler set the UI signal before
  persisting, so a failed marker write would desync the checkbox from disk.
  Reordered to persist first and revert (no signal change, no command) on write
  failure.
- Substantive (docs/QA): the env-override test only covered the disabled path.
  Added an assertion that a non-empty env var also overrides a non-empty custom
  key.
- Substantive (concurrency): confirmed real. `iroh_services::Client` is `Clone`
  with an `Arc<AbortOnDropHandle>` metrics task, and the
  PingServices/RunNetDiagnostics arms clone it into detached spawns. So toggling
  off while a probe was in flight could leave one more push firing until the
  probe finished. Fixed in a follow-up: the two services probes now run in a
  tracked `JoinSet` (`services_probes`), and the SaveApiSecret/SetTelemetryEnabled
  arms `abort_all()` before dropping the client, so every clone is released and
  pushes stop promptly. Finished probe entries are drained before each spawn to
  bound memory. The doc-comment and commit body were updated to match.

Findings deferred to the user (judgment/compliance calls, not silently changed):

- Privacy: marking the Play data types "optional" is arguable, since collection
  is on for every fresh install before the user sees the toggle. A Play reviewer
  could read "optional" as opt-in. Decision needed: mark required, or add a
  first-run consent gate before the first push.
- Privacy: the device id is the user's stable public node id (their connection
  identity), not an isolated random token, so "anonymous" is optimistic
  ("pseudonymous, network-observable" is accurate). Decision needed: reword the
  user-facing strings/docs, or mint an independent random telemetry id.
- Concurrency: the client rebuild awaits inline in the command pump (inherited
  from SaveApiSecret), briefly blocking other commands on a network round-trip.
  Consistent with prior code; left as-is.

Findings discarded as noise: redundant `.clone()` on Copy signals (pre-existing
file-local style); telemetry_pref public-surface test gap (thin wrappers over a
non-injectable global; acceptable).
