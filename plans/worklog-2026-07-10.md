## Progress

### 2026-07-10 - Brainstorm and design approved

Goal: let two devices exchange endpoint ids without copy-pasting a 64-hex
string. Any device shows its id as a QR; a phone scans it with the system
camera and the app opens with the peer id prefilled.

User chose the system-camera + deep-link approach over in-app camera
(getUserMedia in webview) and native camera. Rationale: no in-app camera code,
identical on iOS and Android, and both devices in a face-to-face exchange
already have the app installed so the custom-scheme degradation does not bite.

Design spec written and approved: two pieces.
- Piece 1: QR display on all platforms (qrcode crate -> inline SVG).
- Piece 2: deep-link connect (custom scheme irohdoctor://connect?id=<hex>,
  registered via bundle-mobile.sh, captured into peer_id_input).

### 2026-07-10 - Research results (deep-link capture), verified against source

Findings (tao 0.34.8, wry 0.53.5, dioxus 0.7.9, confirmed from Cargo.lock and
upstream source at the pinned tags):

- **Registration is a config one-liner.** `[deep_links] schemes = ["irohdoctor"]`
  in Dioxus.toml feeds both `android_url_schemes` and `ios_url_schemes` in the dx
  CLI (manifest_mapper.rs:41-46). The iOS plist template emits CFBundleURLTypes;
  the Android manifest template emits an <intent-filter> (VIEW/DEFAULT/BROWSABLE)
  on MainActivity. No bundle-script patch needed, and it survives bundle-mobile.sh
  (that script never touches CFBundleURLTypes or AndroidManifest.xml). Dev builds
  register the scheme too, so no dx-serve testing friction. This kills the earlier
  "registration goes through the wrapper" and "dev-only friction" notes.
- **iOS capture: tao emits `Event::Opened { urls }`** for custom-scheme opens
  (ios/view.rs handle_deep_link). Dioxus surfaces raw tao events via
  `use_wry_event_handler` (not cfg-gated; re-exported through dioxus::desktop,
  aliased by dioxus::mobile). ~10 lines, no objc2 delegate swizzling. Warm start
  works live; cold start should work (tao buffers pre-launch events) but the
  exact ordering is the one unproven point -> mitigate only if device testing
  shows a drop. The objc2 risk is GONE.
- **Android cold-start: the ndk_context context IS the WryActivity** (a real
  Activity, ndk_glue.rs:196-223), so `getIntent().getData()` works over the
  existing android::with_env helper. Add one function.
- **Android warm-start is the only hard part.** tao does not forward
  onNewIntent (wry #1563 open). Correct handling needs launchMode=singleTask +
  a MainActivity.kt onNewIntent/setIntent override + a JNI extern callback,
  all patched post-build in bundle-mobile.sh. Deferrable: cold-start covers the
  scan-when-app-not-running case.
- **dx-ignores-config caveat (from learnings.md).** [application] name and
  [ios] deployment_target are silently ignored in 0.7.9. So [deep_links] must be
  verified by grepping the generated Info.plist + AndroidManifest.xml after a
  build. Fallbacks if broken: iOS [ios.raw] info_plist raw XML; Android post-build
  manifest patch in the wrapper.

## Staff reviews

Round 1 (2026-07-10): four adversarial subagents on the full diff 623f127..HEAD
- Rust idiom/correctness, safety/FFI, concurrency/lifecycle, docs/QA.

Findings and the review-of-reviews (opposing-stance) outcome:

- SURVIVED (fixed):
  - deep_link_channel OnceLock set-once with swallowed error (flagged by 3 of 4
    reviewers). A UI remount orphaned the new receiver -> silent, total loss of
    deep links until restart. Fixed by storing the sender in a Mutex<Option<..>>
    that each new receiver re-registers (75cd4c9).
  - onNewIntent JNI callback could unwind across FFI. No panic path today, and
    extern "system" aborts safely since Rust 1.81, but wrapped in catch_unwind
    as categorical FFI-boundary hygiene (75cd4c9).
  - parse_connect_url filtered the empty id after find_map, not per pair, so
    ?id=&id=abc returned None. Moved the filter inside find_map; added tests for
    that and for whitespace-trimmed links; documented case-sensitivity (67009e0).
  - Added #[must_use] to connect_url/parse_connect_url/resolve_peer_id/
    render_qr_svg per project convention (67009e0).
- DISCARDED (opposing stance held):
  - Verb-first summary for launch_deep_link: matches the file's existing
    getter-doc convention (files_dir, clipboard_text); consistency wins.
  - const CONNECT_PREFIX to avoid a per-render format! alloc: ~21-byte alloc is
    negligible, and a separate literal would split SCHEME's single source of
    truth (the [deep_links] sync note depends on it). Premature.
  - Security notes (exported activity, custom-scheme squatting, no length bound,
    no percent-encode in connect_url): all explicitly note-only. Mitigation is
    already present: a deep link only prefills + switches tab (no auto-connect),
    and the node re-validates the id via EndpointId::from_str.
  - Pre-registration warm-intent drop: unreachable (onNewIntent only fires for a
    fully-running instance).

Post-fix verification: 59 tests pass, desktop + android clippy clean, fmt flags
only pre-existing files.

## Decisions made

- System-camera + deep-link over in-app camera. See design spec.
- Custom URL scheme over universal links (no hosted association files needed).
- Prefill peer id + switch to Connect tab; no auto-dial.
- qrcode crate with svg-only features.
